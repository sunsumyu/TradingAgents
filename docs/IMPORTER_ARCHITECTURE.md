# BaoStock 导入器架构改进方案

## 当前问题

经过多次调试，发现当前架构存在以下根本问题：

### 1. 单进程脆弱性
- 一个进程处理 5000+ 股票，任何崩溃都导致全部停止
- 崩溃原因多样：BaoStock 服务端问题、网络波动、内存泄漏、未捕获异常
- 每次崩溃都需要手动重启

### 2. 脆弱的状态管理
- 本地 JSON 文件 + PostgreSQL 双写，容易不一致
- 状态文件损坏导致进度丢失或重复处理
- 重建状态需要从 PG 扫描，耗时且复杂

### 3. 复杂的并发控制
- 线程超时 → daemon 线程持有 socket → 并发访问崩溃
- 尝试用多进程修复 → Windows spawn 模式问题（pickle、socket、session）
- 每层并发控制都引入新的失败点

### 4. 外部依赖强
- BaoStock 服务不稳定（33% ping 丢包、黑名单、限流）
- 网络问题直接影响整个导入进程
- 无法控制外部服务质量

### 5. 缺乏真正的容错
- 崩溃后需要手动干预
- 没有自动恢复机制
- 没有健康检查和告警

## 已实施的快速修复

### 1. Partial-save 优化
- 失败股票保留已拉取的年份数据
- 重试时只拉取缺失年份
- 减少重复工作

### 2. 超时后 socket 清理
- 超时后主动关闭 socket，唤醒 daemon 线程
- 避免并发访问导致的崩溃
- 但仍然依赖单进程模型

### 3. 看门狗进程
- 独立进程监控导入器健康状态
- 自动重启崩溃的导入器
- 限制重启频率，避免重启循环

## 长期架构方案

### 方案 A：任务队列架构（推荐）

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│   Scheduler │────▶│  Task Queue  │────▶│   Workers   │
│  (single)   │     │ (PostgreSQL) │     │  (pool of   │
└─────────────     └──────────────┘     │  4-8 procs) │
                                          └─────────────┘
                                                 │
                                          ┌────────▼────────┐
                                          │  BaoStock API   │
                                          └─────────────────┘
```

**核心设计：**
1. **任务表** — 每只股票是一个任务，状态存在 PG
2. **Worker 池** — 4-8 个 worker 进程并行处理
3. **无状态** — Worker 无本地状态，崩溃后重启继续
4. **自动重试** — 失败任务自动回到队列
5. **健康检查** — Scheduler 监控 worker 健康

**优点：**
- 一个 worker 崩溃不影响其他任务
- 可以水平扩展（增加 worker 数量）
- 状态完全在 PG，易于监控和调试
- 支持暂停、恢复、优先级调整

**缺点：**
- 需要重构现有代码
- 多进程管理复杂度
- 需要任务队列基础设施

### 方案 B：无状态批处理（简单可靠）

```
┌─────────┐     ┌──────────┐     ┌─────────────┐
│  Cron   │────▶│ Importer │────▶│ BaoStock    │
│ (every  │     │ (single  │     │ API         │
│  5min)  │     │  stock)  │     └─────────────┘
└─────────┘     └──────────┘
                      │
               ┌──────▼──────┐
               │ PostgreSQL  │
               │ (state)     │
               └─────────────┘
```

**核心设计：**
1. **每次一只股票** — 导入器只处理一只股票就退出
2. **Cron 调度** — 每 5 分钟启动一次
3. **状态在 PG** — 从 PG 获取下一只需要处理的股票
4. **简单可靠** — 没有复杂的并发控制

**优点：**
- 极简架构，易于理解和维护
- 崩溃影响最小（只损失当前股票）
- 天然支持并发（多个 cron 实例）
- 状态完全在 PG

**缺点：**
- 速度较慢（串行处理）
- 频繁启动/退出开销
- 需要外部调度器

### 方案 C：混合架构（平衡）

```
┌─────────────┐     ┌──────────────┐
│  Watchdog   │────▶│   Importer   │
│  (monitor)  │     │  (batch of   │
└─────────────┘     │  100 stocks) │
                    └──────────────┘
                           │
                    ┌──────▼──────┐
                    │ PostgreSQL  │
                    │ (state)     │
                    └─────────────
```

**核心设计：**
1. **批量处理** — 每次处理 100 只股票后保存状态
2. **看门狗** — 独立进程监控，崩溃后重启
3. **PG 状态** — 状态完全在 PG，本地文件仅缓存
4. **优雅退出** — 捕获信号，保存进度后退出

**优点：**
- 平衡速度和可靠性
- 架构改动较小
- 易于实施

**缺点：**
- 仍然有单进程风险
- 批量大小需要调优

## 总结

真正的架构问题是**单进程模型 + 脆弱状态管理 + 复杂并发控制**的组合。

短期修复（看门狗 + 错误处理）可以缓解症状，但长期需要**任务队列架构**才能根本解决。

建议采用渐进式改进：短期用看门狗稳定系统，中期用混合架构平衡速度和可靠性，长期用任务队列实现真正的容错和扩展性。
